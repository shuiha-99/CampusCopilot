# Memory Token 用量固定开发/回归集 v1

两条各24消息的固定场景：奖学金样例曾参与摘要提示词调试；转专业样例是本轮新增的合成场景。`manifest.json`锁定输入 SHA-256。两者用于开发与回归，不是独立测试集或真实学生对话。

在项目根目录运行 `python -B -m scripts.evaluate_memory_tokens_v1`，需要本机 Ollama 的 `qwen2.5:7b`。脚本使用生产代码的摘要提示和回答上下文构造方法，按消息1～6生成 v1 摘要、再用消息7～14更新 v2，保留最近10条；对同一问题、证据和模型分别发送完整历史与 Memory。回答两侧只生成1个 Token，以取得真实 Provider 返回的**输入 Token 数**，不评测回答质量。两次摘要的输入加输出 Token 单独合计。

| 场景 | 完整历史回答输入 | Memory回答输入 | 回答输入减少 | 两次摘要总Token | 一次回答后的净变化 |
|---|---:|---:|---:|---:|---:|
| 奖学金 | 717 | 609 | 108（15.06%） | 1102 | 增加994 |
| 转专业 | 648 | 550 | 98（15.12%） | 847 | 增加749 |

“一次回答后的净变化”只比较这两种路径的 Token 总量：`回答输入减少 − 两次摘要输入及输出`。两侧回答均仅生成1个 Token，故回答输出在对照中相同。固定上下文重复提问时，理论上分别需第11次、第9次回答后才可能抵消摘要开销；这是**静态算术示例**，真实连续会话会新增消息、更新摘要、改变提问和模型输出，不能据此宣称生产盈亏点或费用收益。

`results_ollama.json`保存每次 Provider 返回的用量、耗时和摘要文本。摘要关键词检查经一次同义词修正后对已保存结果重评分：把“不应”识别为“不能/不可”的同义限制，未重新调用模型。两例当前检查项均通过，但关键词检查不等于逐句事实核验；尤其奖学金样例没有具体金额数值，不能据此证明不同年度金额准确。旧字符计量的16.12%来自另一次已记录的模型摘要，不能与本次 Token 百分比混成同一次实验。

真实问答 Trace 的 Token 落库另由 `python -B -m scripts.check_token_trace`验证：本地 Ollama 调用、MySQL `ModelAttempt` 与进程内 HTTP `/runs/{run_id}` 读回闭环。流式请求和独立 Memory 压缩请求当前没有请求级 Token Trace；此脚本只验证非流式 Agent 问答。
